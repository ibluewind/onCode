# onCode Architecture Overview

## 1. Purpose

onCode is an air-gapped coding-agent platform inspired by tools such as Cursor, opencode, oh-my-openagent, and Codex.

Its architectural principle is:

> **Central Brain, Local Hands, Shared State**

The central server performs orchestration, planning, reasoning, workflow control, policy, context management, guide retrieval, dependency/security analysis, and audit.

The Local Agent runs on the developer workstation and performs all workspace-bound execution such as file reads, file writes, diff generation, build, test, Git, and local process execution.

The central server MUST NOT directly modify the developer workspace.

## 3. Core Responsibility Boundaries

### 3.1 Central Server

The Central Server owns:

- User / session / project / work-item management
- Workflow state machine
- Agent orchestration
- Context Storage
- Project Catalog search
- Guide Retrieval
- Dependency / vulnerability evaluation
- Authorization / policy checks
- Approval state
- Audit / observability
- LLM inference routing

The Central Server does **not** directly:

- Open arbitrary developer workspace files
- Write developer workspace files
- Run local builds
- Run local tests
- Run local Git commands

These operations MUST go through the Local Agent.

### 3.2 Local Agent

The Local Agent owns:

- Workspace registration
- Workspace boundary enforcement
- File read/search
- File watcher
- Project indexing
- Actual diff generation
- Atomic file apply
- Build
- Test
- Git
- Local process execution
- Local security policy enforcement
- IDE IPC
- Persistent connection to the server

### 3.3 IDE Extension

IDE Extensions are intentionally thin.

They own:

- Chat UI
- Current editor / selection metadata
- Progress display
- User questions
- Design review
- Design approval
- Diff review
- Code approval
- Build/test result navigation

IDE Extensions MUST NOT independently implement workspace mutation, build/test orchestration, or Git automation.

---

## 4. Shared State Model

Agents MUST NOT directly pass large context payloads to each other.

All durable shared state is stored in Context Storage.

Example references:

```text
ctx://projects/PRJ-100/profile
ctx://work-items/WI-100/design/latest
ctx://work-items/WI-100/change-set/current
```

Agents exchange `context_refs`, not ad-hoc direct agent-to-agent context blobs.

The Context Storage is the SSOT for workflow-related shared context.

Private reasoning / hidden chain-of-thought MUST NOT be stored.

## 5. Core Workflow

The primary implementation workflow is:

```text
RECEIVED
→ CLASSIFYING
→ DISCOVERING_CONTEXT
→ ANALYZING_REQUIREMENT
→ RETRIEVING_GUIDE
→ DESIGNING
→ WAITING_DESIGN_APPROVAL
→ ANALYZING_DEPENDENCY
→ IMPLEMENTING
→ REVIEWING
→ SECURITY_REVIEWING
→ PREPARING_CHANGE
→ WAITING_CODE_APPROVAL
→ APPLYING_CHANGE
→ VALIDATING_SYNTAX
→ BUILDING
→ TESTING
→ FINAL_REVIEW
→ COMPLETED
```

For the first technical MVP, some states may be simplified, but the approval and apply boundaries MUST remain.

## 6. Approval Model

Approval types:

```text
DESIGN
CODE_CHANGE
COMMAND
DEPENDENCY_INSTALL
GIT_COMMIT
GIT_PUSH
GIT_MERGE
GIT_REBASE
DESTRUCTIVE_OPERATION
```

The mandatory coding loop is:

```text
PROPOSE
→ APPROVE
→ APPLY
```

Approval MUST be bound to the exact resource being approved, such as:

- change_set_id
- workspace_id
- project_id
- file hashes
- command args
- cwd
- approval resource hash

An approval MUST NOT be reusable for a different resource.

---

## 7. Change Application Model

Implementation agents produce a structured `ProposedChanges` set.

They do **not** directly apply files.

```text
Implementation Agent
      ↓
Structured ProposedChanges
      ↓
Local Agent
      ↓
Compare against current workspace
      ↓
Generate actual diff
      ↓
IDE review / approval
      ↓
Revalidate base hashes
      ↓
Atomic apply
```

The actual user-approved diff MUST be generated by the Local Agent from the current local workspace.

If a base file changed after proposal creation, return a stale-workspace error. Never force-apply.

---

## 8. Project Intelligence

Project Intelligence is local-first.

```text
Local Workspace
   ↓
Scanner / Parser
   ↓
PROJECT_INDEX
   ↓
Delta Sync
   ↓
Central Project Catalog
```

The central catalog stores structural metadata such as:

- path
- language
- module
- symbol
- signature
- summary
- framework metadata
- dependency
- relation
- revision/hash

Full source code is not the default central search unit.

Project search discovers candidate files/symbols.

Actual source MUST be fetched from the Local Agent before implementation.

---

## 9. Project Search Architecture

Search uses a hybrid model:

```text
Central Project Catalog
→ discover relevant files / symbols

Local Agent
→ return actual current source
```

Initial search backend:

- exact symbol/path match
- keyword match
- PostgreSQL FTS
- trigram
- relation expansion

Vector DB is not required for MVP.

---

## 10. Guide Architecture

Guide processing is split into two systems.

### Ingestion / Curation

```text
Original document
→ Conversion
→ Docling / Markdown / Structured JSON
→ Normalization
→ Section split
→ Category classification
→ Summary / keyword extraction
→ Admin review
→ Publish
```

### Runtime Retrieval

```text
Published Guide Release
→ metadata filtering
→ exact / keyword / FTS / trigram search
→ priority / rule ranking
→ mandatory rule injection
→ top-k
→ guide.read
```

Guide scope priority:

```text
PROJECT_RULE
>
ORGANIZATION_RULE
>
FRAMEWORK_RULE
>
LANGUAGE_RULE
>
GENERAL_RULE
```

---

## 11. Dependency Architecture

All dependency discovery and installation must use internal Nexus.

Public registries are prohibited.

Dependency decision order:

```text
existing project dependency
→ safe compatible version
→ approved Nexus package
→ alternative package
→ redesign
→ minimal custom implementation
```

Security-sensitive functionality such as cryptography, password hashing, certificate validation, OAuth protocol handling, and signature validation should not be custom-implemented when a vetted dependency exists.

---

## 12. Security Model

Policy decisions:

```text
ALLOW
APPROVAL_REQUIRED
DENY
```

Local Agent risk levels:

```text
READ
WRITE
EXECUTE
HIGH_RISK
DESTRUCTIVE
```

Defense layers:

```text
Agent Permission
→ Tool Gateway Policy
→ Workflow Guard
→ User Approval
→ Local Policy
→ Execution Validation
```

A server-side ALLOW cannot override an organization or local DENY.

## 13. Technology Decisions

Current recommended ADR decisions:

| Area | Decision |
|---|---|
| Central Server | Java + Spring Boot |
| Server architecture | Modular Monolith initially |
| Local Agent | Go |
| Server ↔ Local Agent | gRPC bidirectional streaming |
| IDE ↔ Local Agent | localhost WebSocket + JSON |
| Main state store | PostgreSQL |
| Redis | not required for MVP |
| Structural parser | Tree-sitter |
| Semantic parsing | language-specific adapters when needed |
| Workflow | PostgreSQL persistent state machine + lease |
| Change model | Structured ProposedChanges + Local actual diff |
| Project search | Local index + central catalog + local source read |
| Inference | onCode Inference Gateway → vLLM |
| Artifact storage | NFS/NAS abstraction initially |
| Repository | Monorepo initially |

---

## 14. MVP Priority

The first meaningful MVP is:

```text
Developer Request
→ project search
→ source read
→ design
→ design approval
→ implementation proposal
→ local diff
→ code approval
→ atomic apply
→ build
→ test
→ fix loop
```

Do not attempt to implement the entire final architecture before this loop works reliably.
