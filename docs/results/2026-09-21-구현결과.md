## 슬라이스 4 — 등록 루트 actual diff와 승인 후 apply

### 구현 내용

서버는 파일을 쓰지 않는다. IDE에 Apply 버튼은 없다. 등록된 `-workspace` 원문으로 actual diff를 만들고, 서버가 `APPLYING_CHANGE`를 보낸 뒤에만 Local Agent가 기존 `workspace.apply_changes`를 한 번 호출한다.

#### 동작

1. **기동 (`oncode-agent -workspace`)**
   - Registry에 루트를 등록하고 발급된 `WS-…` ID를 Hub에 넣는다.
   - 등록이 없으면 예전처럼 `ws-local`과 빈 원본 actual diff. apply 대기열은 없다.

2. **actual diff**
   - 워크스페이스가 있으면 `Workspace.Propose`로 현재 파일 해시·unified diff를 만들고 `ProposalStore`에 둔다.
   - 서버 `change_set_id`가 프로토콜 CHG UUID가 아니면 로컬에서 새 CHG ID를 발급한다. MODIFY/DELETE/RENAME의 `base_hash`는 디스크에서 채운다.
   - 경로 탈출·없는 파일은 fail-closed. bind하지 않는다.
   - 등록이 없으면 기존 `actualdiff.FromProposed` (빈 원본 또는 주입된 OldContent).

3. **apply**
   - `diff.review` 바인딩 후에만 대기열에 넣는다. `can_apply`는 계속 false.
   - `workflow.progress` `APPLYING_CHANGE`에서만 apply. `REJECTED`면 대기를 지운다.
   - 대기열은 apply 시도 때 비운다. 두 번째 `APPLYING_CHANGE`는 재적용하지 않는다.
   - 원문이 바뀌면 stale 오류. 강제 적용 없음.
   - 서버 하니스 `workspace.apply_changes`는 여전히 호출하지 않는다.

4. **IDE**
   - `apply.result`를 Output `onCode`에만 표시. 워크스페이스 I/O 없음.

## 슬라이스 5 — 도구 채널 gRPC REQUEST/RESPONSE

- 날짜: 2026-09-21
- 계획서: `docs/plans/2026-09-21-작업계획.md`
- 슬라이스: **5 — 도구 채널 gRPC**

### 구현 내용

채팅·승인은 기존처럼 EVENT다. 도구 호출만 같은 `LocalAgentSession.Open` 스트림의 REQUEST/RESPONSE로 보낸다. proto 필드 번호는 재사용하지 않았다. ToolGateway·에이전트 런타임은 proto 타입을 보지 않는다.

#### 동작

1. **서버 `GrpcToolSession`**
   - 에이전트가 Open하면 송신 스트림을 붙인다. 끊기면 대기 호출을 UNAVAILABLE로 끝낸다.
   - 와이어 `call_id`/`message_id`는 UUID v7이다. 게이트웨이 CALL-12hex는 응답에 그대로 돌려준다.
   - work_item_id는 Envelope에 넣지 않는다 (서버 12 hex는 Go `ids.Validate`를 통과하지 않음).

2. **`RoutedLocalAgentChannel`**
   - 세션이 열려 있으면 gRPC. 없으면 인메모리 하니스. 테스트는 하니스 경로를 유지한다.

3. **Local Agent `propose_changes`**
   - 스크립트 속기(`path`/`operation`/`content`)를 받는다. 등록 워크스페이스가 하나면 그걸 쓰고, CHG ID와 `base_hash`를 채운다.
   - 경로 탈출·없는 파일은 거절한다.

4. **정책**
   - AGENT `workspace.apply_changes`는 게이트웨이에서 채널 전에 거부. 승인 후 apply는 슬라이스 4처럼 Local Agent Hub만.

#### 주요 파일

| 구분 | 경로 |
|------|------|

| 라우팅 | `server/.../toolgateway/RoutedLocalAgentChannel.java` |
| 스트림 | `server/.../api/grpc/AgentSessionService.java` |
| propose | `local-agent/internal/tools/workspace/tools.go` |
| Registry | `local-agent/internal/workspace/workspace.go` (`Sole`) |

## 슬라이스 6 — apply 완료(COMPLETED) + 동일 내용 안내

- 날짜: 2026-09-21
- Phase: 3 잔여
- 계획서: `docs/plans/2026-09-21-작업계획.md`
- 슬라이스: **6 — apply.completed → COMPLETED, unchanged diff**

### 구현 내용

수동 E2E에서 apply SUCCESS 뒤 재연결 시 `APPLYING_CHANGE`가 반복되던 문제를 닫는다. Local Agent가 apply 성공을 서버에 알리면 SSOT가 `COMPLETED`로 간다. 제안이 현재 파일과 같으면 디스크를 다시 쓰지 않고도 완료 처리한다.

#### 동작

1. **워크플로**
   - `WorkflowState.COMPLETED` 추가. 허용 전이: `APPLYING_CHANGE → COMPLETED`만.
   - `nextLinear(APPLYING_CHANGE)`는 empty. 선형 스텁이 완료로 뛰지 않는다.
   - `WorkflowEngine.completeAfterApply`가 COMPLETED로 전이하고 work item status도 COMPLETED.

2. **서버**
   - EVENT `apply.completed` → `ApprovalIntake.applyCompleted` → progress `COMPLETED`.
   - 이미 COMPLETED면 idempotent progress만. 서버는 디스크/apply 도구를 부르지 않는다.
   - `restore`는 COMPLETED면 pending 없이 progress만.

3. **Local Agent**
   - apply SUCCESS(또는 unchanged skip) 후 `apply.completed` EVENT 송신.
   - unified diff에 `+`/`-` 줄이 없으면 `unchanged=true` + 안내 문구. APPLYING 시 rewrite 없이 completed.
   - progress `COMPLETED`면 `lastWorkItemID`·bind·pending 정리.

4. **IDE**
   - `diff.review`의 `unchanged`/`message` 표시. 동일 내용이면 승인 모달 문구 변경.
   - progress `COMPLETED`/`REJECTED`면 저장된 work item 삭제(재연결 시 APPLYING 반복 방지).
   - progress 라벨에 APPLYING/COMPLETED/REJECTED 추가.
