## 슬라이스 1 — Local Agent WebSocket IPC와 thin client 연결

### 구현 내용

IDE는 서버에 붙지 않는다. Local Agent가 `127.0.0.1` WebSocket+JSON만 열고, VS Code 확장은 그 소켓에 재연결한다. 채팅·승인·gRPC는 없다.

#### 동작

1. **IDE Bridge (`local-agent/internal/idebridge`)**
   - listen 주소는 루프백 IP만 (`127.0.0.1`, `::1`). `0.0.0.0` / 사설·공인 주소는 `New`에서 거부.
   - 기본 포트 0(ephemeral). 실제 포트는 state dir의 `ide-ipc.json`에 기록.
   - 기동 시 32바이트 세션 토큰 발급. 재시작(`New` 재호출)마다 회전. 종료 시 디스커버리 파일 삭제.
   - 연결은 query `token` 또는 `Authorization: Bearer`. 없거나 틀리면 업그레이드 없이 401.
   - Origin이 웹 호스트면 403. 빈 Origin / `null` / `vscode-file` / 루프백 http는 허용.
   - 첫 메시지 `ide.register` → `ide.registered` (`ide_client_id`, `agent_id`). 워크스페이스 도구는 호출하지 않음.

2. **에이전트 기동**
   - `oncode-agent`가 시그널 대기 전에 Bridge를 연다.
   - `ONCODE_IDE_IPC_BIND`, `ONCODE_IDE_IPC_PORT`로 덮어쓸 수 있다. bind가 루프백이 아니면 기동 실패.

3. **VS Code 확장 (`ide/vscode/`)**
   - `ide-ipc.json`만 읽는다 (에이전트 state dir). 워크스페이스 파일 I/O·빌드·테스트 없음.
   - 연결 → `ide.register` → 끊기면 지수 백오프 재연결. 명령 `oncode.reconnect`.
   - 연결 URL 호스트는 항상 `127.0.0.1` (파일의 bind가 변조돼도 루프백 밖으로 나가지 않음).

#### 주요 파일

| 구분 | 경로 |
|------|------|
| Bridge | `local-agent/internal/idebridge/*` |
| 설정 | `local-agent/internal/config/config.go` |
| 기동 | `local-agent/cmd/oncode-agent/main.go` |
| WS 의존성 | `go.mod` (`github.com/gorilla/websocket v1.5.3`) |
| 확장 | `ide/vscode/extension/activate.ts`, `ide/vscode/ipc/*` |
| 확장 테스트 | `ide/vscode/tests/*` |

#### 하지 않은 것

- 채팅, progress, question, 설계/코드 승인 UI
- work item 생성, 서버 gRPC (슬라이스 2)
- protocol JSON Schema 승격
- Phase 2 V1/V2 DDL
- VS Code Marketplace 패키징 / 실제 IDE 수동 설치 검증

## 슬라이스 2 — Chat / progress / gRPC 전송 어댑터

- 날짜: 2026-09-17
- Phase: 3 — IDE Interaction (`docs/tasks/PHASE_03.md`)
- 계획서: `docs/plans/2026-09-17-작업계획.md`
- 슬라이스: **2 — Chat / progress / gRPC**

### 구현 내용

경로: `IDE WS+JSON → Local Agent → Server gRPC Envelope 스트림`. IDE는 서버에 붙지 않는다. 도구 실행은 기존 인메모리 `LocalAgentChannel`을 유지한다. 핸들러는 proto 생성 타입을 보지 않는다.

#### 동작

1. **프로토콜**
   - `LocalAgentSession.Open` bidirectional stream of 기존 `Envelope` (필드 번호 재사용 없음).
   - Go `protocol/grpcadapt`: 논리 `messages.Envelope` ↔ protobuf. Java 서버는 gRPC 레이어에서만 proto를 쓰고 `ChatIntake`에는 Map/도메인 객체를 넘긴다.

2. **Local Agent gRPC 어댑터**
   - `transport.Stream`이 `Transport`를 구현. `transport.Memory` 유지.
   - `ONCODE_SERVER_GRPC_ADDR`가 있을 때만 outbound 연결. 비어 있으면 채팅은 `UNAVAILABLE`.
   - `idesession.Hub`: `chat.submit` / `question.answer`를 서버 EVENT로 전달, `workflow.progress` / `question.ask`를 IDE로 broadcast.
   - `chatctx.ValidateSubmit`: `content`/`source` 등 본문 키 거부. 허용은 message, work_item_id, path, line range.

3. **서버**
   - loopback gRPC (`oncode.grpc.port`, 기본 9443). 테스트는 `oncode.grpc.port=0`.
   - `ChatIntake`: 경로가 있으면 work item 생성 후 설계 승인 대기까지 진행 이벤트. `work_item_id`면 재개. 소스 본문 거부. 파일 없으면 TEXT 질문.
   - `question.ask` 타입 팩토리: SINGLE_SELECT / TEXT / CONFIRM.
   - 도구 gRPC 라우팅은 하지 않음 (인메모리 채널 유지).

4. **VS Code**
   - 명령 `oncode.chat.send`. 활성 편집기 **경로와 1-based line range만** 첨부.
   - Output에 progress. QuickPick / InputBox / Yes-No로 질문 답변.
   - 워크스페이스 파일 내용 읽기·쓰기·빌드·테스트 없음.

#### 주요 파일

| 구분 | 경로 |
|------|------|
| proto | `protocol/schemas/proto/oncode_tool.proto` (`LocalAgentSession`) |
| Go 어댑터 | `protocol/grpcadapt/*`, `protocol/gen/toolv1/*` |
| Go transport | `local-agent/internal/transport/grpc.go` |
| IDE 중계 | `local-agent/internal/idesession/*`, `local-agent/internal/chatctx/*` |

#### 하지 않은 것

- 설계/코드 승인 UI, actual diff, apply (슬라이스 3)
- Server↔Agent WebSocket 어댑터
- 도구 호출을 gRPC로 옮기기 (인메모리 `LocalAgentChannel` 유지)

## 슬라이스 3 — 승인·diff·재연결 복원

- 날짜: 2026-09-17
- Phase: 3 — IDE Interaction (`docs/tasks/PHASE_03.md`)
- 계획서: `docs/plans/2026-09-17-작업계획.md`
- 슬라이스: **3 — 승인·actual diff·재연결**

### 구현 내용

설계 리뷰와 코드/diff 리뷰는 다른 이벤트다. IDE에 보이는 diff는 Local Agent unified diff이며 모델 제안 JSON이 아니다. 승인은 `engine.decide`만 하고 `workspace.apply_changes`는 호출하지 않는다. V1/V2 DDL은 그대로 두고 바인딩 추가는 `context_entry`에만 둔다.

#### 동작

1. **서버 `ApprovalIntake`**
   - 채팅이 설계 대기에 들어가면 `design.review` (summary, design_identity=sha256, can_apply=false).
   - `approval.decide`는 `approval_id` + `resource_id` + `work_item_id` + `workspace_id` + (DESIGN: `design_identity` / CODE: `diff_hash`)가 맞을 때만 소비.
   - 설계 REJECT → `REJECTED`. 설계 APPROVE → `implementAndReview` → `change.proposed` (ProposedChanges JSON, unified diff 없음).
   - 코드 승인은 Local Agent `approval.bind`로 저장된 `diff_hash`와 일치해야 한다. 일치하면 `APPLYING_CHANGE`. apply 도구 없음.
   - `session.restore`는 현재 상태 progress + 대기 승인을 다시 보낸다.

2. **Local Agent**
   - `change.proposed`를 받아 `actualdiff.FromProposed`로 unified diff + `sha256:` 해시를 만들고 IDE에는 `diff.review`만 보낸다.
   - 같은 해시로 `approval.bind`를 서버에 보낸다.

3. **VS Code**
   - 설계: 모달 Approve/Reject. actual_diff 없음.

## 슬라이스 외 — bindDiff 롤백 / diff 승인 창

- 날짜: 2026-09-17
- 계획서: `docs/plans/2026-09-17-작업계획.md` (슬라이스 외)
- 이슈: ISS-004

### 구현 내용

코드 승인 창이 뜬 직후 `ApprovalIntake.bindDiff`가 `UnexpectedRollbackException`을 내고 gRPC 스트림이 끊겼다. VS Code 모달은 Approve/Reject만 있어 닫히지 않는 것처럼 보이거나, 복원 이벤트가 같은 창을 다시 쌓았다.

- `bindDiff`는 `requireUsable` 예외를 잡지 않고 `findById`로 CODE REQUESTED만 받는다.
- `requireUsable`은 조회 실패 예외에 `noRollbackFor`.
- 없는 컨텍스트는 `ContextService.find` (예외 없음).
- gRPC `onNext` 예외는 error EVENT로 바꾸고 스트림을 유지한다.
- IDE는 같은 `approval_id` 모달을 중복 표시하지 않는다.

하지 않은 것: Apply, 실 vLLM, protobuf Unsafe 경고 제거 (JDK 25 + protobuf-java 4.29.3 경고일 뿐).
